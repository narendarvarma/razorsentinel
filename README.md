# RazorSentinel

## AI-Powered Merchant Early-Warning & What-If Intelligence

> **This project is an independent prototype created for the Razorpay Open Track. It is not an official Razorpay product.**

---

## Project Overview

RazorSentinel is an AI-powered merchant early-warning system that detects emerging merchant-level business problems before they become significant losses. It answers seven critical questions:

1. **What** is going wrong?
2. **When** did it start?
3. **Why** is it probably happening?
4. **How serious** is it?
5. **How much revenue** could be at risk?
6. **What happens if** the situation gets worse?
7. **What should** the merchant investigate?

## Problem Statement

Payment gateways process millions of transactions daily. When a merchant's payment success rate drops, it directly impacts revenue. Current monitoring systems use **fixed universal thresholds** (e.g., "alert if success < 95%"), which creates two problems:

1. **False alarms** for merchants whose normal rate is below the threshold
2. **Missed anomalies** for high-performing merchants whose rate drops within the "normal" range

**Example:**
- Merchant A: Normal success = 98%, Current = 91% → **CRITICAL anomaly** (7pp drop)
- Merchant B: Normal success = 92%, Current = 91% → **NORMAL** (within baseline)

The same 91% rate produces completely different severity assessments.

## Why It Matters

- Revenue loss from undetected payment degradation compounds quickly
- Fixed thresholds cannot capture merchant-specific behavioral patterns
- Root cause identification enables faster incident response
- What-if simulation enables proactive decision-making

## Solution

RazorSentinel implements a **merchant-relative anomaly detection system** that:

1. Learns each merchant's own historical baseline using rolling statistics
2. Computes z-scores against the merchant-specific baseline
3. Detects anomalies based on statistical deviation, not fixed thresholds
4. Investigates root causes with transparent contribution scoring
5. Estimates financial impact with clear calculation traceability
6. Provides what-if simulation for decision support
7. Uses LLM only as an explanation layer (never for computation)

## Innovation

### Core Differentiator: Merchant-Relative Baselines

Instead of universal thresholds, RazorSentinel compares each merchant against **its own historical behavior**:

```
z = (current - rolling_mean) / rolling_std
```

Severity levels:
- |z| < 1: NORMAL
- 1 ≤ |z| < 2: WATCH
- 2 ≤ |z| < 3: HIGH
- |z| ≥ 3: CRITICAL

### Transparent Root Cause Analysis

When an anomaly is detected, the system investigates multiple signals and ranks them by contribution score, calculated from z-score magnitudes — not generated by an LLM.

### What-If Intelligence

The simulator dynamically recalculates all downstream metrics when a parameter changes, using real transaction data — no fake numbers.

### LLM Safety

The LLM is used **only** as an explanation layer. It receives pre-computed analytics context and is instructed to never invent numbers, calculate financial values, or introduce unsupported facts.

## Dataset Methodology

- ~10,000 synthetic transactions for 2 merchants
- Seeded PRNG (Mulberry32) for reproducibility
- Realistic hourly traffic patterns (weekday/weekend variation)
- Payment method distribution: UPI 55%, Card 30%, Netbanking 15%
- Amount distributions vary by payment method
- **One deterministic anomaly**: UPI success drops from ~98% to ~82% for 3 hours on Merchant A

## Merchant-Relative Baseline

The baseline is computed by comparing the **same time window** across different days:

- **Anomaly window**: 14:00-17:00 on the anomaly day
- **Baseline**: Same 14:00-17:00 window on all prior normal days

This eliminates hour-of-day variance and produces meaningful z-scores. A 2% drop during low-traffic hours produces a different z-score than the same drop during peak hours.

## Anomaly Detection

1. Compute hourly metrics for each merchant
2. Identify the anomaly time window
3. Compare against the same time window on normal days
4. Compute z-scores for all key metrics
5. Classify severity based on z-score magnitude
6. Flag anomaly if any metric reaches HIGH or CRITICAL

## Root Cause Methodology

When an anomaly is detected:

1. Calculate z-scores for all individual signals (UPI, Card, Netbanking, Checkout, Refund)
2. Identify signals with problematic z-scores (negative for success metrics, positive for refund)
3. Compute contribution score: `contribution = |z_score| / sum(|z_scores|) × 100`
4. Rank causes by contribution descending

**Key guarantee**: Contribution scores are calculated by the analytics engine, never by the LLM.

## Financial Impact Methodology

Revenue at risk is calculated as:

```
1. UPI rate gap = baseline_upi_rate - current_upi_rate
2. Lost UPI transactions = total_upi_count × rate_gap
3. Lost revenue = lost_transactions × avg_upi_amount
4. Daily revenue at risk = lost_revenue × (24 / anomaly_hours)
5. 7-day projected risk = daily_risk × 7
```

All estimates are labeled **MODEL ESTIMATE** and are never presented as guaranteed future losses.

## What-If Methodology

The simulator uses real transaction data:

1. Filter transactions for the anomaly window
2. Recalculate: `simulated_success = round(total_upi × new_rate)`
3. Recalculate revenue using average UPI amount × new success count
4. Compute revenue at risk and risk level
5. All values update dynamically when the slider moves

**No fake numbers. No hardcoded results.**

## LLM Safety

### What the LLM does:
- Receives structured analytics context
- Generates natural language explanations
- Answers supported questions about the incident

### What the LLM NEVER does:
- Invent numbers
- Calculate financial values
- Modify analytical results
- Answer unsupported questions

### Offline fallback:
If the LLM API is unavailable, deterministic template responses are used with real computed values.
